# Quili: instructions for coding agents

One app, implemented twice: **Windows** (`windows/`, C# / WPF, .NET 8) and **macOS** (`mac/`, Swift / AppKit). See `README.md` for what it does and how to build it.

## The rule: both platforms stay identical

**Any change made to the Windows code or the macOS code must be replicated exactly in the other one.** Behavior, defaults, text, constants, timings, colors, sizes, geometry, error messages and design all have to match. A change is not finished until both sides are updated.

- Treat the platform you were asked to change as the starting point and port the change to the other platform in the same piece of work. Don't leave the second platform for later.
- When the two disagree and you weren't asked to change either, report it; don't silently pick a side.
- Match the other platform's *outcome*, using each platform's own idiom (UI Automation vs Accessibility API, WPF vs AppKit, DPAPI vs Keychain). Don't invent new behavior on one side.
- If a platform genuinely can't do something the same way, do the closest equivalent and add it to the list of intentional differences below, in the same change.
- Keep user-facing strings, the default paraphrase instruction, endpoints, JSON fields, limits, timeouts and retry rules identical.
- Verify both: `./build.sh windows debug` and `./build.sh mac debug` compile-check without packaging (Windows needs the .NET 8 SDK; macOS needs Xcode). If you can only build one platform on this machine, say so explicitly in your summary.

## Intentional platform differences

Keep this list current. Anything not listed here is expected to match.

- API key storage: DPAPI-encrypted in `settings.json` (Windows) vs Keychain (macOS); other settings in `settings.json` vs `UserDefaults`.
- Run at startup: the `Run` registry key vs `SMAppService`. The label reads "Start with Windows" vs "Start at login".
- Single instance: named mutex vs a bundle-identifier check.
- Tray icon vs menu-bar item: "Exit" vs "Quit"; Windows also opens Settings on tray double-click.
- Notifications: tray balloon vs `osascript` banner.
- Field detection: UI Automation vs the Accessibility API. macOS additionally enables the web accessibility tree of Chromium / Electron / Firefox apps.
- Permissions: macOS needs Accessibility, and optionally Screen Recording for `FieldEdge` (Windows samples pixels without a permission).
- Text-field fonts: Segoe UI vs the system font.
- Lone-surrogate cleanup exists only on Windows (Swift strings can't hold them).
- Streaming: both clients send `"stream": true` and read server-sent events (`delta` = text so far, each replacing the previous; then `done` or `error`), showing the text in the click-through bubble above the button (below when there is no room) and only offering the result once `done` arrives (for paraphrase and translate the field is replaced only after Apply in the review bubble, see "Review before replace"). Windows reads the stream with `StreamReader`, macOS with `URLSession.bytes(...).lines` (which skips blank lines, so an event is handled on its `data:` line). A server that answers plain JSON still works.
- Overlay cursor: the macOS overlay always shows the regular arrow pointer (requested). Windows still shows a hand over the actions and a size-all cursor on the green button.
- One-time migration from the app's former name "Paraphrase Tool": Windows copies `%APPDATA%\ParaphraseTool\settings.json` and moves the old `Run` entry; macOS copies the old `UserDefaults` domain `com.ferdibot.paraphrasetool` and the old Keychain item (macOS asks once to allow reading it). These legacy names are the only places the old name should remain.
- Summarize Slack thread (`/api/summarize-thread`, started from the Summarize button): both read the open thread pane of the Slack desktop app through the accessibility tree (UIA vs `AXUIElement`), send it to the server, show the summary in a tall, top-aligned bubble anchored to the button (closable from the start, and it stays until it is closed) and copy it to the clipboard; Slack is never written to. Differences: macOS checks the Accessibility permission first; Slack is found by bundle id `com.tinyspeck.slackmacgap` vs process name `slack`. The reader is heuristic (Slack's tree is undocumented) and its own log lines carry only counts and roles, but when a summary is requested the whole thread text that is sent is written to the debug log (deliberate, as a debugging aid: the log then holds thread content, and it is cleared once it passes 1 MB).
- Caret avoidance: a caret tracker (`Platform/CaretTracker.cs` / `Accessibility/CaretTracker.swift`) polls the focused field's caret every 100 ms on its own thread (UIA `TextPattern` selection range / AX `AXSelectedTextRange` + `AXBoundsForRange`; a zero-length range first, else the character before the caret (not after a line break), else the one after) and reports a thin box in screen coordinates only when it moves. While that box touches the ✦ button at its *default* place (inflated by 6 x 4 dip, judged at the default place so it cannot flip back and forth) the button slides to the right so that its left edge is 5 pt/dip right of the caret (one button width right of its default place when the caret is unknown; never left of the default place; kept on the screen) in 0.16 s, and it keeps following the caret at that 5 pt gap while the caret keeps moving under it, and it slides back to the default place as soon as the caret has left (for example after a new line). A button the user dragged is never moved by this; a new field, hiding the overlay or a busy request resets it. Same on both platforms.
- Summarize button: while Slack is in front and Slack's own "Summarize thread" button is on screen, a round green sparkle button (icon only; "Summarize thread on Quili" is its tooltip) sits just left of Slack's own icon-only "Summarize thread" button (a button whose short name says so, or whose direct child text does; 8 dip to its left, on its right when the screen has no room) and summarizes that thread when clicked. That button is the only "a thread is open" signal for showing Quili's button, and "thread" must match as a whole word so Slack's "Threads" view does not count; its frame only has to be at least 12 dip, as it is a small icon button (Slack's is 28). To find it quickly the search first locates the thread pane (a group/landmark labelled "Thread" or "Utas", only as a shortcut to a small subtree) and then looks inside it for a button whose name, help text or id says "summarize" (looser than the exact "summarize thread" used when there is no pane). When nothing is found it logs the header buttons' type|name|help|id|size (at most every 20 s, never message text) so an unexpected Slack layout can be diagnosed. There is no menu-bar / tray item for it: the button is the only way to start a summary. When reading, the order is: the smallest region of at least 6 lines around Slack's button, widened by climbing while the ancestor is still a side pane (at most 60% of the window wide) so the parent message that started the thread, which sits above the "N replies" divider, is included, then a group/landmark labelled "Thread" or "Utas", then the smallest region around the focused message box. A background watcher polls every second (searching the tree at most every 2 s while no pane is known, re-measuring the cached pane otherwise). The summary bubble anchors to the button; the summary bubble is closable from the first moment ("Reading the thread…", the streaming text, the finished summary; a × at its top-right, and the bubble then takes clicks; clicking it before the summary is done also cancels the request) and the finished summary stays open until it is closed (no auto-close; it can be long, so the bubble scrolls with the mouse wheel); the summary's `**bold**` (the server marks the most important information that way) is drawn bold in the bubble with the markers hidden, an unclosed `**` while streaming staying bold to the end, and only for summaries (`markdown` / `SetBody`), while the copy on the clipboard uses Slack's `*bold*` (`TextHygiene.slackMarkup` / `SlackMarkup`); closing fades the bubble out over 0.25 s (`BubbleWindow.fadeOut()` / `FadeOut()`), and any new bubble or hide cancels a fade in progress, (paraphrase/translate previews stay click-through). Same on both platforms; only the UI toolkit differs (non-activating `NSPanel` vs a `WS_EX_NOACTIVATE` WPF window). Pause hides it. Tooltip: macOS draws its own small tooltip window 0.4 s after the pointer settles on the button (native tooltips don't show for a panel while another app is active); Windows uses the WPF `ToolTip`.
- Thread text format: each container of the Slack pane becomes one line; a message header, the author's name then its time (a few short runs, then a run like "Just now", "22 minutes ago" or "2:53 PM", the time not first), is written `Author [time]` so the summarizer can tell who said what (`/api/summarize-thread`'s prompt explains it). Font weight is not used: Slack's accessibility tree does not expose it. The name must come from a button (how Slack renders authors) or look like a name (capitalised words), and `@mentions` never count; a lone time is a hover time and stays as is. Slack (Chromium) only exposes the replies near the visible part of the pane, so a long thread is read by scrolling: the reader scrolls the pane to the top, reads a screenful, steps down about 70% of the pane at a time (at most 40 steps, 15 s), and merges the views by the lines they share (relative times such as "32 minutes ago" are ignored when matching, since they can roll over meanwhile). Whether the pane moved (and so whether it reached the top or bottom) is decided from the on-screen positions of the list's items, not from the text read, because Slack renders a buffer of messages beyond the viewport and a real scroll can leave the text unchanged (macOS; Windows reads the scroll percentage). If the views stop overlapping it steps back and takes smaller steps; if nothing scrolls, what was visible is used. macOS scrolls smoothly with scroll-wheel events in small slices at the pane's position (it checks each move went the expected way by the views' overlap) and, when Slack ignores those, asks the accessibility tree to bring the first or last rendered message of the thread's list into view (`AXScrollToVisible`, which jumps); the log line says how many moves were smooth and how many were jumps. The pane always goes to the top first, is read downwards to the bottom, and is scrolled back to the top when done (wherever it started); Windows uses the UIA ScrollPattern the same way. The text sent is grouped per message: each message (its header line and the lines below, up to the next header) is wrapped in `{{` and `}}`, messages are separated by a blank line, and `{`/`}` inside a message are escaped as `\{`/`\}` (`ThreadFormat.messages` / `Messages`; a header is recognised by its `[time]` part). When the thread is too long the oldest whole messages are dropped. Interface controls and chrome are dropped by `ThreadNoise`, including the pane's title line ("Thread dbagroup"). The debug log also records a text-free outline of the captured region (roles/types, child counts, text lengths) to diagnose missing messages.
- "Write debug log" setting (on by default): when off, nothing is written to `debug.log` at all; switching it in Settings leaves one "debug log turned off/on in Settings" line, so the log shows when it was disabled. macOS reads it from the `loggingEnabled` preference inside `DebugLog` itself; Windows keeps it in `Settings.LoggingEnabled` and pushes it to `DebugLog.Enabled` at startup and on Save.
- "Mock server (offline)" setting: when on, Save starts a built-in loopback server (`127.0.0.1`, system-picked port, answers `/api/paraphrase`, `/api/translate` and `/api/summarize-thread` with fixed canned text, streaming `delta`/`done` events like the real server; 404 elsewhere) and every action is sent to it, needing neither a server URL nor an API key. Turning it off and saving stops the server and goes back to the real one; it is also started at launch while the setting is on. Differences: macOS uses `NWListener` (Network.framework) and shows a notification banner if it cannot start; Windows uses a `TcpListener` (so no URL reservation or admin rights are needed) and shows a message box.
- Tone button and chips: the pill's cells, left to right, are Settings (gear), Tone (Material "tune" icon; a click does nothing), Summarize (Material "notes" icon), EN, Paraphrase, then the round button; the expanded pill is 210 wide (28 + 5 x 36 + 2). Each cell has its own tooltip ("Settings", "Tone", "Summarize", "Translate to English", "Paraphrase"; the round button "Text Tool", "Cancel" while busy). Windows uses WPF `ToolTip`s; macOS draws its own small label after 0.4 s (`TooltipWindow`, as for the Summarize button; native tooltips do not show for a panel while another app is active), on the side opposite the tone bar for the Tone cell so they never overlap. Hovering the Tone button (not while a request runs) shows a bar of four chips (Formal, Casual, Shorter, Fix grammar) centred on that button, above the pill, or below it when the pill is docked below its field. It hides 250 ms after the pointer has left both the Tone button and the bar, and whenever the overlay hides, a request starts or the field changes. The pill stays expanded for as long as the bar is shown (`keepExpanded` / `KeepExpanded`). The selected tone is a setting (`tone` / `Tone`, the preset id, empty = none; saved immediately when a chip of the bar is clicked, on Save from Settings) and its chip is highlighted (tint, green-ink text, green border) in the bar and in Settings → "Paraphrase tone", where clicking the selected chip clears it. There is no instruction text box: the built-in instruction is `Settings.baseInstruction` / `Settings.BaseInstruction` and the request's `style` (paraphrase only) is that instruction followed, after a blank line, by the selected tone's adjustment line ("Tone adjustment: ... Keep everything else above."; `Tone.applied(to:)` / `Tone.Presets[..].AppliedTo`; the base is cut to stay within 1000 chars, never the adjustment; the texts are the same on both platforms), so the base instruction's rules always apply. Same on both platforms; the bars are non-activating windows (`NSPanel` vs `WS_EX_NOACTIVATE`).
- Settings and Privacy & apps windows: raised and focused once when opened, then ordinary windows (macOS `window.level = .normal` after `orderFrontRegardless`; Windows `Topmost` toggled on then off), so another app's window can cover them.
- Undo and compare: after a successful replace the app keeps the field, the text as it was read, what was written and whether only a selection was replaced, for 15 s, and shows an **Undo** / **Original** bar next to the pill (the tone bar takes its place while it is showing). A new request, a summary, another field, hiding the overlay and the 15 s timeout drop it. **Original** toggles a closable, non-markdown bubble with the old text. **Undo** brings the field's app forward if needed (else puts the original on the clipboard and says "Focus changed"), then pastes the original over the whole field, or, for a selection, finds the written text in the field (macOS: in the `AXValue` string, selected through `AXSelectedTextRange`; Windows: `TextPattern` `FindText`) and pastes over it; when it cannot, the original is copied to the clipboard and "Couldn't undo automatically" is shown.
- Cursor over the chip bars and closable bubbles: macOS claims the regular arrow on every pointer event (the panel never activates, so the app underneath would show its I-beam); Windows windows set their own cursor, so nothing extra is needed.
- Settings and Privacy & apps cards have a 2 px outline in the logo green (`#3DBE4A`, the header badge's colour) so two open windows stay apart (macOS draws it as a click-through `CardBorder` view above the content; Windows sets it on the card's `Border`).
- Per-app list: setting `appFilterMode` / `AppFilterMode` (`hide`, default, or `only`) and `appFilterList` / `AppFilterList` (one entry per line or comma-separated, `#` starts a comment line, case-insensitive). In `only` mode an empty list hides Quili everywhere. The focus tracker skips an app that is not allowed (log: `skip app filter: <name>`); the Summarize button is never filtered. Differences: macOS matches the bundle id, the localized name or the executable name; Windows matches the process name, with or without `.exe`.
- Redact before sending: settings `redactSecrets` (default on) and `redactEmails` (default off; only applies while `redactSecrets` is on). Before a request, the text is masked: PEM private key blocks, the password in a `scheme://user:password@` URL, `Bearer` tokens, well-known token shapes (`sk-`, `ghp_`, `github_pat_`, `xox*-`, `AKIA`, `AIza`, JWTs), `key=value` secrets (`password`, `secret`, `api key`, `token`, ...) and, if enabled, email addresses are replaced by `QXKEY<n>QX` (the same value gets the same placeholder). The streamed and the final answer get the originals back; a summary only has the placeholders relabelled `[hidden value <n>]`. If a placeholder is missing from a paraphrase or translation, nothing is written and an error explains it. The log records only how many values were hidden, and the server prompts (`PLACEHOLDER_RULE` in senwich-bot) tell the model to copy the placeholders unchanged. Same rules and wording on both platforms.
- Review before replace (paraphrase and EN translate; summaries are unchanged): the streaming preview bubble stays click-through, but when the final text arrives the field is NOT touched. The bubble becomes a tall, closable, non-markdown review bubble: the result with the words that changed shown on a soft-blue background (`#D6E8FF` fill, `#1F4E8C` text) and a 40 dip footer with **Discard** (white, outlined) and **Apply** (green) buttons; the × discards too. It stays until Apply, Discard / ×, a new request, a different field (or none), Pause or a summary starting. **Apply** regains focus like a replace, checks that a whole-field read is still what the field holds (letters and digits compared; a field whose value cannot be read passes; a selection is verified by the selection restore), else notifies "Text changed" / "The field changed while you were reviewing, so nothing was replaced. Run it again." and drops it; after a successful write the Undo bar is offered as before. The changed words come from `TextDiff.changedRanges` (`Services/TextDiff.swift` / `Core/TextDiff.cs`, same algorithm): both texts are split into tokens (a run of letters/digits, a run of whitespace, or one other character), an exact longest-common-subsequence over the tokens marks the result tokens that are not shared, changed words separated only by whitespace merge into one range, whitespace alone is never highlighted, and above 4,000,000 token pairs nothing is highlighted.
- Recent rewrites (History): while "Keep my last 10 rewrites on this computer" is on (default; Privacy & apps), each finished paraphrase, translation and summary (thread or selection) is stored, newest first, 10 at most, in `~/Library/Application Support/Quili/history.json` (`%APPDATA%\Quili\history.json`): id, time, kind (`paraphrase` / `translate` / `summarize`), the app in front, the original text (cut to 2000 chars; empty for Slack thread summaries) and the result. Turning the setting off and saving clears the file. Hovering the Paraphrase (✦) button shows a one-chip **History** bar (same design, same hover rules and 250 ms grace as the tone bar; one hover bar at a time) that opens the **Recent rewrites** window: the Settings card design with a 420 dip scrolling list (title, "Today 11:42" / "Yesterday 09:10" / "24 Oct 11:42", the app, the original in muted text up to 2 lines, the result up to 3 lines, **Copy result** / **Copy original** chips that read "Copied" for 1.5 s), **Clear history** and **Close**, with a message when it is empty or history is off.
- Secret warning (setting `warnSecrets`, default on; Privacy & apps): a watcher polls the focused field's text every 600 ms on its own queue (at most the first 20000 characters, skipped while the text is unchanged), counts the distinct secrets the Redactor finds (emails never count) and reports changes on the UI thread. While the count is above 0 and the setting is on, the round button shows a 14 px orange (`#F5A524`) circle with a white ring and a white bold **!** at its top-right (collapsed and expanded), and its tooltip, when not busy, reads "This text looks like it contains a secret". Nothing leaves the computer.
- Suggested next action (always running; independent of the secret setting): from the same text, length under 20 → no hint; more than 30 % of the letters above U+024F, or at least 6 words of 2+ letters of which fewer than 12 % are common English words (`the`, `and`, `is`, `to`, `of`, ...) → **Translate**; otherwise 800 characters or more → **Summarize**. Collapsed, the round button gets a 16×12 pale green tag at its top-left ("EN" or the notes glyph); open, the suggested cell keeps a soft green background and its tooltip ends in " (suggested)". The two rule sets (`LanguageHint`) must stay identical on both platforms.
- Reply-aware writing (setting `useContext`, default **off**; Privacy & apps): only when Slack is in front and the action is Paraphrase or Translate. Quili reads the last 6 messages (at most 3000 characters, oldest dropped first) around the focused input, without scrolling, in the thread format (`{{Author [time]` … `}}`, `{`/`}` escaped), masks secrets in them (placeholders numbered after the text's own, never restored or required) and sends them as `"context"` (max 6000 characters; the server wraps it in a `<context>` block that can never give instructions). Never stored in History. The review bubble shows "Used {n} messages from Slack as context" ("1 message" for one) in muted 12 px text at the footer's left. Any failure reading the context sends the text without it.
- Check setup / Check for updates (menu-bar / tray items below Pause): **Check setup…** lists lines with ✓ / ✗: settings (or "Mock server (offline) is on"), the server (an empty POST to `/api/paraphrase` with the key: 422 works, 401 key rejected, 503 no key on the server, other status, or can't reach it; 10 s) and, on macOS only, the Accessibility permission with an **Open Accessibility Settings** button (Windows: "Windows accessibility: ready"). **Check for updates…** reads `tag_name`/`html_url` of the latest GitHub release (`VersionCompare` compares the dotted numbers after a leading "v"): "Quili is up to date", "Quili {tag} is available" with an offer to open the page, or "Couldn't check for updates". With **Check for updates once a day** on (default), startup checks silently when the last check is over 24 h old, stores the time after every attempt and only notifies when a newer release exists.
- Summarize selected text (`POST /api/summarize-text`, `TextAction.summarizeText`): from the pill's Summarize cell (the focused field's selection, or the whole field when nothing is selected; the field is never written) or from the menu-bar / tray item **Summarize selected text** (whatever is selected in the app in front, editable or not: the focused element's selected text through the Accessibility API / UI Automation, else Cmd/Ctrl+C with the clipboard restored; nothing selected: "No text selected" / "Select the text you want summarized in any app, then choose Summarize selected text."). The summary streams into a tall, closable bubble (anchored to the pill, or to the mouse pointer for the menu item; closing it earlier cancels the request), stays until closed, is copied without its `**` markers ("Text summarized" / "The summary was copied to the clipboard.") and goes into the history. Secrets are relabelled like in thread summaries.
- "Privacy & apps" window: opened from a link in Settings (which was already too tall), with the sections **Before sending** (redact secrets, redact emails, warn about secrets, use Slack context), **On this computer** (keep history, daily update check) and **Apps**, i.e. the redact checkboxes, the history checkbox, the "Only show Quili in the apps listed below" checkbox and the app list, and its own Save / Cancel. The hint for the list differs: bundle ids and names on macOS, process names on Windows.
- Check setup, third line: macOS checks the Accessibility permission with `AXIsProcessTrusted()` ("Accessibility permission: granted" / "Accessibility permission: not granted. Open System Settings → Privacy & Security → Accessibility", with an extra **Open System Settings** button, shown as an `NSAlert`); Windows has no such permission and always prints "Windows accessibility: ready" (shown as a message box). The Windows menu is the tray menu, the macOS one the menu-bar menu.
- Log location: `%APPDATA%\Quili\debug.log` vs `~/Library/Logs/Quili/debug.log`.

## Changelog

`CHANGELOG.md` lists what changed for users. **Every medium-sized or larger change goes into it in the same change that makes it**: a new feature or setting, a behaviour change someone would notice, or a bug fix someone would have hit. Typo fixes, pure refactors, comments and doc-only tweaks don't need an entry.

- Add it under `## Unreleased`, in `### Added`, `### Changed` or `### Fixed`, newest first, written for a user (what they see), not for a developer (no file or function names). Say which platforms it affects; a change that is on both platforms (see the rule above) needs one entry.
- For a visible UI fix or feature, add before/after or demo screenshots under `docs/images/` and show them in the entry when you have them.
- When a release is cut (the `VERSION` file is bumped and tagged), rename `## Unreleased` to `## <version>` and start a new empty `## Unreleased`.

## Commits

**Every medium-sized or larger change is committed as soon as it is done**, so the history shows what changed and when. That is the same bar as the changelog (a feature, a visible behaviour change, a notable bug fix, a larger refactor); typo fixes and tiny tweaks can wait and ride along with the next commit.

- **Always commit through `tools/commit.sh "<message>"`, never a bare `git commit`.** Each argument is one paragraph of the message (the first is the subject), so `tools/commit.sh "Add the tone bar" "Why or details" "<trailer lines>"`. The script stages everything, makes sure the repo-local author is the personal identity (`ferdinandimas`, see below) and commits; it refuses an empty message and an empty commit, and it never pushes.
- This repository only ever uses the personal GitHub identity (`Ferdinand Dimas <ferdinandimas@gmail.com>`, remote `git@github-personal:ferdinandimas/...`), never the work account or email; the global git config is the work one, so the script enforces the local one.
- Commit locally only. **Never push** unless asked: a push is a separate request.
- One commit per change, with the code, its docs (`CHANGELOG.md`, `README.md`, this file) and any screenshots together, so the commit tells the whole story. Don't mix unrelated work in one commit.
- Write the message for a reader of the history: a short imperative subject saying what the change does, then a few lines on the why or the notable details. Say in it when a platform could not be compiled.
- Commit only once both platforms carry the change (see the rule at the top), and after the macOS side compiles when you can build it. If the build fails, fix it first; don't commit a broken tree.
- Never commit secrets or build output (`dist/`, `.p12` / `.pem` / `.key`).

## Practical notes

- `mac/build.sh` signs with the self-signed "Quili Dev" certificate when it exists in the keychain (create it once with `mac/make-signing-cert.sh`), otherwise ad-hoc. With an ad-hoc signature macOS forgets the Accessibility permission after every rebuild: remove and re-add `dist/mac/Quili.app` in System Settings → Privacy & Security → Accessibility. Never commit `.p12` / `.pem` / `.key` files.
- `dist/` is build output and is not tracked.
- The version comes from the `VERSION` file; both build scripts stamp it into the app.
- Commit and push: see *Commits* above (commit after medium-sized or larger changes; push only when asked).
